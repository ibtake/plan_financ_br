1. Preparação (uma vez só)

Alguns itens (V-03, V-04, V-05) são publicados pelo Supabase CLI. Faça isto uma vez:

  1. Instale o CLI (se ainda não tiver): 
    npm install -g supabase
  2. Faça login — abre o navegador para autorizar: 
    supabase login
  3. Vincule o projeto local ao remoto. Pegue a Reference ID em Project Settings → General (é o <ref> da URL https://<ref>.supabase.co): 
    cd C:\Users\igorp\Downloads\Planejador
supabase link --project-ref <ref>

Antes de qualquer migração: faça backup do banco no painel → Database → Backups. E exporte seus dados pelo app (botão de backup JSON) antes de testar a importação (V-05).

2. V-08 — Revogar CREATE no schema public Baixa

Comece por aqui: é só rodar SQL no painel, sem CLI. Objetivo: impedir que qualquer papel crie objetos no schema public (o que poderia "sombrear" suas funções).

  1. No painel do Supabase, abra SQL Editor (menu lateral) → New query.
  2. Verifique se o problema existe. Cole e rode: 
    select has_schema_privilege('public', 'public', 'CREATE');
  3. Leia o resultado:
    • false → já está seguro, não precisa fazer mais nada neste item.
    • true → siga para o passo 4.
  4. Se deu true, rode a correção: 
    revoke create on schema public from public;
  5. Confirme rodando de novo o select do passo 2 — agora deve retornar false.

Isso não quebra nada: sua aplicação não cria tabelas/funções em runtime, e as migrações continuam funcionando porque rodam como dono do banco.

3. V-09 — Confirmar rate limit do Auth Baixa

Não é código: é uma verificação de painel. O bloqueio de tentativas de login que existe no app roda no navegador e é burlável (basta limpar o storage). A defesa real é o rate limit do próprio Supabase Auth.

  1. No painel, abra Authentication → Rate Limits (em versões novas: Authentication → Attack Protection / Rate Limits).
  2. Confirme que há limite ativo para sign-in / token (tentativas por hora, por IP).
  3. Se estiver desativado ou muito alto, ajuste para um valor sensato (o padrão do Supabase já protege; só confirme que não foi afrouxado).
  4. Anote os valores encontrados para registrar no relatório final da auditoria.

Enquanto estiver no painel de Authentication, aproveite para confirmar as pendências operacionais: "Enable Signup" desligado (cadastro público fechado) e ausência de buckets em Storage.

4. V-04 — Migração do log de segurança Média

Problema: ao atingir 50 eventos/hora, a função log_security_event faz return e descarta tudo — inclusive eventos críticos. Um atacante pode gastar a cota de propósito e depois agir sem deixar rastro.

Solução: eventos critical sempre gravam; a cota vale só para info/warning; e, ao estourar, grava-se um resumo rate_limited por hora em vez de silêncio total.

Nunca reaplique o schema.sql inteiro sobre o banco. Crie um arquivo de migração novo. Ele será aplicado incrementalmente.

  1. Crie o arquivo de migração pelo CLI (ele gera o nome com timestamp): 
    supabase migration new v04_log_rate_limit
    Isso cria supabase/migrations/<timestamp>_v04_log_rate_limit.sql.
  2. Cole exatamente este conteúdo no arquivo criado (assinatura idêntica à atual, só muda o miolo do rate limit): 
    create or replace function public.log_security_event(
  p_event_type text,
  p_severity   text default 'info',
  p_details    jsonb default '{}'::jsonb,
  p_user_agent text default null
)
returns void
language plpgsql
security definer
set search_path = public, pg_temp
as $$
declare
  v_uid   uuid := auth.uid();
  v_email text;
  v_event_count integer;
begin
  if v_uid is null then
    return;
  end if;

  select count(*) into v_event_count
  from public.security_events
  where user_id = v_uid
    and created_at > now() - interval '1 hour';

  -- V-04: nunca descartar eventos criticos; cota vale so para info/warning
  if v_event_count >= 50 and coalesce(p_severity, 'info') <> 'critical' then
    -- grava no maximo 1 resumo por hora, em vez de silenciar tudo
    if not exists (
      select 1 from public.security_events
      where user_id = v_uid
        and event_type = 'rate_limited'
        and created_at > now() - interval '1 hour'
    ) then
      select email into v_email from auth.users where id = v_uid;
      insert into public.security_events (
        user_id, event_type, severity, email, user_agent, details
      ) values (
        v_uid, 'rate_limited', 'warning', v_email,
        left(coalesce(p_user_agent, ''), 400),
        jsonb_build_object('reason', 'hourly log quota reached')
      );
    end if;
    return;
  end if;

  select email into v_email from auth.users where id = v_uid;

  insert into public.security_events (
    user_id, event_type, severity, email, user_agent, details
  ) values (
    v_uid,
    p_event_type,
    coalesce(p_severity, 'info'),
    v_email,
    left(coalesce(p_user_agent, ''), 400),
    coalesce(p_details, '{}'::jsonb)
  );
end;
$$;
  3. Aplique a migração no banco remoto: 
    supabase db push
  4. Confirme no SQL Editor que a função foi recriada: 
    select prosrc from pg_proc where proname = 'log_security_event';
    O texto deve conter rate_limited.

5. V-05 — Importação atômica Média

src/hooks/useSupabaseFinance.js — função importData (linha ~232)

Problema: hoje o código chama supabase.rpc('delete_my_data') e só depois insere. Se um insert falhar (rede, constraint, RLS), os dados antigos já foram apagados e não há como voltar atrás.

Há duas formas de resolver. Escolha uma.

Opção A — Validar tudo antes de apagar (mais simples, só frontend)

Monte e valide os quatro conjuntos antes de chamar o delete. Se algo estiver malformado, aborta sem tocar no banco. Estrutura sugerida:

const importData = useCallback(async (data) => {
  // 1. montar tudo primeiro (sem tocar no banco)
  const txs  = Array.isArray(data.transactions) ? data.transactions.map(normalizeTransaction) : transactions
  const cats = Array.isArray(data.categories) && data.categories.length ? data.categories : categories
  const nextBudgets = data.budgets && typeof data.budgets === 'object' ? data.budgets : budgets
  const nextGoals   = Array.isArray(data.goals) ? data.goals.map(/* ... */) : goals

  // 2. V-05: validar ANTES de destruir. Aborta se o payload for invalido.
  if (!cats.every(c => c && c.id) || !txs.every(t => t && t.id)) {
    throw new Error('Backup invalido: importacao cancelada, seus dados foram preservados.')
  }

  // 3. so agora apaga e insere
  await supabase.rpc('delete_my_data')
  const results = await Promise.all([ /* ...upsert/insert como hoje... */ ])
  const failure = results.find(r => r.error)
  if (failure) reportError(failure.error)
  // ...
}, [/* deps */])

Ainda existe uma janela pequena entre o delete e o insert (se a rede cair no meio). Reduz muito o risco, mas não é 100% atômico.

Opção B — RPC transacional (mais robusta, recomendada)

Uma única função no Postgres apaga e insere na mesma transação: se qualquer insert falhar, o Postgres reverte tudo automaticamente.

  1. Crie a migração: 
    supabase migration new v05_replace_my_data
  2. Cole no arquivo (ajuste as colunas conforme suas tabelas): 
    create or replace function public.replace_my_data(p_data jsonb)
returns void
language plpgsql
security definer
set search_path = public, pg_temp
as $$
declare
  v_uid uuid := auth.uid();
begin
  if v_uid is null then
    raise exception 'nao autenticado';
  end if;

  -- tudo dentro da mesma transacao: erro = rollback automatico
  delete from public.transactions where user_id = v_uid;
  delete from public.budgets      where user_id = v_uid;
  delete from public.goals        where user_id = v_uid;
  delete from public.categories   where user_id = v_uid;

  insert into public.categories (user_id, id, name, icon, color, type)
  select v_uid, x.id, x.name, x.icon, x.color, x.type
  from jsonb_to_recordset(p_data->'categories')
    as x(id text, name text, icon text, color text, type text);

  insert into public.transactions (user_id, id, /* ... */)
  select v_uid, x.id, /* ... */
  from jsonb_to_recordset(p_data->'transactions')
    as x(id text /* , ... */);

  -- budgets e goals de forma analoga
end;
$$;

grant execute on function public.replace_my_data(jsonb) to authenticated;
revoke execute on function public.replace_my_data(jsonb) from public, anon;
  3. Aplique: 
    supabase db push
  4. No frontend, troque o delete+Promise.all por uma chamada só: 
    const { error } = await supabase.rpc('replace_my_data', {
  p_data: { transactions: txs, categories: cats, budgets: nextBudgets, goals: nextGoals }
})
if (error) throw error   // dados antigos permanecem intactos

Recomendação: Opção B. O rollback do Postgres garante tudo-ou-nada de verdade.

6. V-03 — Limite real de corpo na Edge Function Média

supabase/functions/admin-users/index.ts (linhas 81-84 e 109-114)

Problema: o limite é checado pelo header content-length, que o cliente controla. Com Transfer-Encoding: chunked não há content-length, então a checagem é ignorada e o corpo pode ter qualquer tamanho.

Solução: ler os bytes de verdade e cortar em MAX_BODY_BYTES (16 KB) antes de fazer o JSON.parse.

  1. Abra o arquivo e localize o bloco atual do content-length (linhas 81-84). Ele pode continuar como um "atalho" (rejeita cedo quando o header já declara excesso), mas não pode ser a única barreira.
  2. Substitua a leitura do corpo (linhas 109-114) por uma versão que mede os bytes reais: 
    let body: Record<string, unknown>
try {
  // V-03: le os bytes reais; nao confia no header content-length
  const raw = new Uint8Array(await request.arrayBuffer())
  if (raw.byteLength > MAX_BODY_BYTES) {
    return response(request, 413, { error: 'Requisição muito grande.' })
  }
  body = JSON.parse(new TextDecoder().decode(raw))
} catch {
  return response(request, 400, { error: 'Corpo da requisição inválido.' })
}

    arrayBuffer() já materializa o corpo inteiro na memória. Como o teto é 16 KB, isso é seguro — não há streaming ilimitado.

  3. Faça o deploy só desta função: 
    supabase functions deploy admin-users
  4. Teste o caminho feliz: faça uma ação de admin normal pelo app e confirme que continua funcionando.
  5. Teste o bloqueio (opcional) enviando um corpo grande com um JWT válido — deve responder 413.

7. V-06 — CSP com host Supabase exato Baixa

vercel.json (linha ~19, header Content-Security-Policy)

Problema: connect-src usa *.supabase.co. Se houver um XSS, dados poderiam ser enviados para qualquer projeto Supabase. Fixar o host exato fecha essa porta.

  1. Descubra sua Reference ID (o <ref> de https://<ref>.supabase.co) em Project Settings → General.
  2. No vercel.json, na diretiva connect-src, troque o curinga pelo host exato: 
    connect-src 'self' https://*.supabase.co wss://*.supabase.co;
connect-src 'self' https://<ref>.supabase.co wss://<ref>.supabase.co;

    Mantenha a variante wss:// se o app usa Realtime (websockets).

  3. Faça commit e deixe a Vercel publicar (ou vercel --prod).
  4. Após o deploy, confirme o header no ar: 
    curl -I https://SEU-APP.vercel.app | grep -i content-security-policy
    Deve mostrar o host exato, sem *.

Lembrete: se um dia você trocar de projeto Supabase, precisará atualizar este host aqui também. Foi por isso que V-07 (remover 'unsafe-inline' do style-src) foi recusada — alto custo de refatoração para ganho baixo; segue como risco residual aceito.
