1. Antes de começar

Regra da auditoria: nenhum arquivo é alterado sem sua confirmação a cada passo. Este manual descreve o que mudar; a aplicação real deve ser feita por você (ou autorizada explicitamente por item).

  • Backup completo antes de qualquer migração no Supabase: painel → Database → Backups (ou pg_dump).
  • Exporte um backup dos seus dados pelo próprio app (JSON) antes de testar a importação (V-05).
  • Anote a referência do projeto Supabase (o <ref> da URL https://<ref>.supabase.co) — necessário para V-06.
  • Tenha o Supabase CLI instalado e logado para publicar a Edge Function e as migrações (supabase login, supabase link).

2. Correções de código (frontend)

Estas mudanças entram no bundle e só têm efeito após novo deploy na Vercel (git push → build automático). Não exigem nada no painel Supabase.

V-02 · CSV Injection na exportação Média

src/utils/exporters.js — função csvCell

Neutralize os prefixos perigosos (= + - @, TAB e CR) prefixando com apóstrofo antes de escapar as aspas:

function csvCell(value) {
  let s = String(value ?? '')
  // V-02: neutraliza formula injection (Excel/LibreOffice)
  if (/^[=+\-@\t\r]/.test(s)) s = "'" + s
  return `"${s.replace(/"/g, '""')}"`
}

Impacto: nenhum no app. Uma célula que começava por esses caracteres passa a exibir um apóstrofo inicial ao abrir no Excel.

V-10 · Upload de ícone aceita SVG Baixa

src/utils/iconUpload.js — linha ~17 (ALLOWED_TYPES)

Remova image/svg+xml da lista de tipos aceitos, deixando apenas rasters:

const ALLOWED_TYPES = [
  'image/png',
  'image/jpeg',
  'image/webp',
  // 'image/svg+xml',  // removido em V-10
]

Risco já era próximo de zero (a imagem é redesenhada em <canvas> e só o PNG é guardado). Esta é uma remoção de superfície opcional.

V-11 · localStorage de ícones não validado Baixa

src/contexts/IconContext.jsx (linhas ~11-19) e src/components/AppIcon.jsx (linha ~25)

Ao ler o valor guardado, aceite somente strings que sejam claramente um PNG em base64. Adicione um guard antes de usar como src:

function isSafePngDataUrl(v) {
  return typeof v === 'string' && v.startsWith('data:image/png;base64,')
}

// ao ler do localStorage / antes de passar para <img src=...>
const icon = isSafePngDataUrl(stored) ? stored : null

Aplique o mesmo guard nos dois arquivos: no contexto (ao carregar) e no AppIcon (ao renderizar).

3. Supabase — Edge Function admin-users (V-03) Média

supabase/functions/admin-users/index.ts — linhas ~81-84

Substitua a confiança no header content-length por uma leitura real com corte em MAX_BODY_BYTES, antes do JSON.parse:

const MAX_BODY_BYTES = 16 * 1024 // ajuste ao seu payload real

async function readLimitedJson(request: Request) {
  const reader = request.body?.getReader()
  if (!reader) return {}
  const chunks: Uint8Array[] = []
  let total = 0
  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    total += value.length
    if (total > MAX_BODY_BYTES) {
      reader.cancel()
      throw new Response('Payload muito grande', { status: 413 })
    }
    chunks.push(value)
  }
  const buf = new Uint8Array(total)
  let off = 0
  for (const c of chunks) { buf.set(c, off); off += c.length }
  return JSON.parse(new TextDecoder().decode(buf))
}

Use readLimitedJson(request) no lugar de request.json(). Trate o throw devolvendo a resposta 413.

Publicar

supabase functions deploy admin-users

Mantenha verify_jwt = true e a checagem de Origin. Confirme o limite real do seu maior lote de importação antes de fixar MAX_BODY_BYTES.

4. Supabase — migração do log de segurança (V-04) Média

supabase/schema.sql — log_security_event (linhas ~311-320)

Nunca reaplique schema.sql sobre a base existente. Crie uma nova migração em supabase/migrations/ conforme o AGENTS.md.

Objetivo: ao estourar a cota (50/hora), não descartar eventos críticos e registrar um resumo em vez de silenciar tudo. Crie o arquivo de migração (nome com timestamp) recriando a função:

-- supabase/migrations/<timestamp>_v04_log_rate_limit.sql
create or replace function public.log_security_event(...)
returns void
language plpgsql
security definer
set search_path = public, pg_temp
as $$
declare
  recent int;
begin
  select count(*) into recent
  from public.security_events
  where user_id = auth.uid()
    and created_at > now() - interval '1 hour';

  -- V-04: eventos 'critical' sempre gravam; a cota vale para info/warning
  if recent >= 50 and p_severity <> 'critical' then
    -- grava no maximo 1 resumo por hora, em vez de silenciar tudo
    if not exists (
      select 1 from public.security_events
      where user_id = auth.uid()
        and event_type = 'rate_limited'
        and created_at > now() - interval '1 hour'
    ) then
      insert into public.security_events(user_id, event_type, severity, detail)
      values (auth.uid(), 'rate_limited', 'warning', 'Cota de log atingida');
    end if;
    return;
  end if;

  insert into public.security_events(...) values (...);
end;
$$;

Ajuste os parâmetros/nomes de coluna à assinatura real da sua função. Aplique com:

supabase db push

5. Supabase — importação atômica (V-05) Média

src/hooks/useSupabaseFinance.js (linhas ~237-243) + nova RPC no Supabase

Hoje importData() chama delete_my_data e só depois insere — se um insert falha, os dados antigos já se perderam. Duas abordagens (escolha uma):

Opção A — RPC transacional (recomendada)

Crie uma migração com uma função que apaga e insere na mesma transação, recebendo o payload como jsonb:

-- supabase/migrations/<timestamp>_v05_replace_my_data.sql
create or replace function public.replace_my_data(p_data jsonb)
returns void
language plpgsql
security definer
set search_path = public, pg_temp
as $$
begin
  delete from public.transactions where user_id = auth.uid();
  delete from public.budgets      where user_id = auth.uid();
  delete from public.goals        where user_id = auth.uid();
  delete from public.categories   where user_id = auth.uid();

  insert into public.categories   select ... from jsonb_...(p_data->'categories');
  insert into public.transactions select ... from jsonb_...(p_data->'transactions');
  -- demais coleções...
end;  -- erro em qualquer insert => rollback automatico de tudo
$$;

grant execute on function public.replace_my_data(jsonb) to authenticated;
revoke execute on function public.replace_my_data(jsonb) from public, anon;

No frontend, troque a sequência delete+insert por uma única chamada:

const { error } = await supabase.rpc('replace_my_data', { p_data: payload })
if (error) throw error  // dados antigos permanecem intactos

Opção B — validar tudo antes (sem RPC nova)

Valide o payload inteiro (schema, tipos, limites) antes de chamar delete_my_data. Menos robusto que a Opção A (ainda há janela entre delete e insert), mas evita destruir dados por payload malformado.

Recomendação: Opção A. O rollback do Postgres garante o tudo-ou-nada.

6. Supabase — revogar CREATE no schema public (V-08) Baixa

Primeiro verifique no SQL Editor se o problema existe:

select has_schema_privilege('public', 'public', 'CREATE');

Se retornar true, endureça (idealmente como migração, para ficar versionado):

revoke create on schema public from public;

Confirme antes que sua aplicação não cria objetos em public em runtime (não cria — o schema é fixo). Migrações continuam funcionando pois rodam como owner.

7. Supabase — confirmar rate limit do Auth (V-09) Baixa

Não é correção de código — é verificação de painel. A barreira de tentativas de login no cliente (sessionStorage) é burlável; a defesa real é o rate limit do Supabase Auth.

  • Painel → Authentication → Rate Limits.
  • Confirme limites ativos para sign-in / token (tentativas por hora por IP).
  • Registre os valores no relatório final da auditoria.

8. Vercel — CSP com host Supabase exato (V-06) Baixa

vercel.json — linha ~19 (header Content-Security-Policy, diretiva connect-src)

Troque o curinga *.supabase.co pelo host exato do seu projeto (o <ref> anotado no passo 1):

"connect-src 'self' https://*.supabase.co wss://*.supabase.co"
"connect-src 'self' https://<ref>.supabase.co wss://<ref>.supabase.co"

Atenção a ambientes: se homologação e produção usam projetos Supabase diferentes, cada um precisa do seu host. Formas de tratar:

  • Manter dois vercel.json por branch/ambiente, ou
  • Gerar o header via variável de ambiente no build.

Após editar, faça git push — a Vercel reconstrói e reaplica os headers.

Verificar o header no ar

curl -sI https://SEU-APP.vercel.app | grep -i content-security-policy

Confirme que aparece o host exato e não mais *.supabase.co.
