2. Antes de começar

2.1 Backup

  1. Painel do Supabase → selecione o projeto → Database → Backups.
  2. Confirme que existe um backup recente. Se o plano permitir, dispare um manual.
  3. Exporte também pelo próprio app: aba Configurações → exportar dados, e guarde o arquivo fora do repositório.

2.2 Confirme o projeto correto

Anote a Project Ref em Project Settings → General. Ela aparece na URL da API como https://<PROJECT_REF>.supabase.co. Confira antes de cada passo — não misture homologação e produção.

2.3 Localize o UUID da sua conta

  1. Authentication → Users.
  2. Localize a linha do seu e-mail administrativo.
  3. Clique na linha e copie o campo User UID — formato xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx.
  4. Cole apenas no campo de secret do Supabase. Não coloque em arquivo do projeto, commit, issue ou print.

Se a sua conta administrativa ainda não existe (porque o cadastro público será desligado), crie-a agora, antes do passo 3: Authentication → Users → Add user → Create new user, com e-mail e senha forte, marcando Auto Confirm User.

3. Supabase — desativar o cadastro público

O arquivo supabase/config.toml já contém enable_signup = false, mas esse arquivo só vale para ambiente local / CLI. No projeto hospedado, a chave é o painel. Sem este passo, qualquer pessoa ainda consegue criar conta chamando a API direto.

  1. Authentication → Sign In / Providers (ou Providers → Email).
  2. Desmarque Allow new users to sign up. Salve.
  3. Ainda em Authentication → URL Configuration:
    • Site URL: a URL de produção da Vercel, ex. https://seu-app.vercel.app
    • Redirect URLs: adicione a URL de produção e http://localhost:5173
  4. Em Providers → Email, mantenha Confirm email ativado.

Confirmar que o cadastro está bloqueado

Depois de salvar, teste no terminal (substitua os dois placeholders; a anon key é pública por natureza):

curl -s -X POST "https://<PROJECT_REF>.supabase.co/auth/v1/signup" \
  -H "apikey: <ANON_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"email":"teste-bloqueio@example.com","password":"SenhaDeTeste!2026"}'

Resposta esperada: erro com signup_disabled / “Signups not allowed for this instance”. Se vier um usuário criado, o passo 3 não foi salvo — repita.

4. Supabase — banco de dados

4.1 O que executar

Execute o arquivo supabase/schema.sql inteiro. Ele traz, entre outras coisas:

  • is_token_valid() — invalida token emitido antes da última troca de credenciais
  • has_required_aal() — exige AAL2 no banco para quem tem MFA verificado
  • RLS + force row level security em profiles, categories, transactions, budgets, goals, security_events
  • Trigger prevent_owner_change() contra troca de dono de registro
  • log_security_event() com rate limit de 50 eventos/hora

É seguro rodar sobre banco já existente. Conferi instrução por instrução: o arquivo usa create table if not exists, create or replace function, drop policy if exists + recriação e drop trigger if exists + recriação. Não há drop table, truncate nem delete de dados. O próprio cabeçalho do arquivo declara todas as instruções idempotentes.

O supabase/migrations/README.md orienta a não usar schema.sql no lugar de migração incremental. Essa regra vale para alterações futuras: daqui pra frente, cada mudança deve virar um arquivo próprio em supabase/migrations/. Para esta atualização, como não existe nenhum arquivo de migração, o schema.sql idempotente é o caminho correto.

4.2 Como executar

  1. Painel do Supabase → SQL Editor → New query.
  2. Confirme no topo que o projeto é o correto (homologação primeiro).
  3. Abra supabase/schema.sql, copie todo o conteúdo e cole.
  4. Clique em Run.

A última instrução do arquivo já é a verificação — o resultado deve listar as 6 tabelas com rls_ativa = true e contagem de políticas maior que zero.

4.3 Consultas de verificação

-- 1. RLS ativa e forçada nas 6 tabelas
select relname as tabela, relrowsecurity as rls, relforcerowsecurity as rls_forcada
from pg_class
where relnamespace = 'public'::regnamespace
  and relname in ('profiles','categories','transactions','budgets','goals','security_events')
order by relname;

-- 2. Funções de segurança criadas
select proname, prosecdef as security_definer
from pg_proc
where pronamespace = 'public'::regnamespace
  and proname in ('is_token_valid','has_required_aal','log_security_event',
                  'prevent_owner_change','set_updated_at','handle_new_user','delete_my_data')
order by proname;

-- 3. O papel anon não pode ter nenhum grant em public
select grantee, table_name, privilege_type
from information_schema.role_table_grants
where table_schema = 'public' and grantee = 'anon';
-- esperado: 0 linhas

-- 4. Dados preservados (compare com o total anterior ao passo 4)
select
  (select count(*) from public.transactions) as lancamentos,
  (select count(*) from public.categories)   as categorias,
  (select count(*) from public.goals)        as metas,
  (select count(*) from public.budgets)      as orcamentos,
  (select count(*) from public.profiles)     as perfis;

Efeito colateral esperado e desejado: depois deste passo, quem tem MFA verificado só enxerga os próprios dados com token AAL2. Se você entrar sem confirmar o código do autenticador, as listas aparecerão vazias. Isso é a política has_required_aal() funcionando, não perda de dados — a consulta 4 acima prova que as linhas continuam lá.

5. Supabase — Edge Function admin-users

5.1 Secrets

Painel → Edge Functions → Secrets (ou Project Settings → Edge Functions). Cadastre exatamente estes dois:

NomeValorObservação
APP_ADMIN_USER_IDS UUID obtido no passo 2.3 Plural. Vários admins = separados por vírgula, sem espaço extra
APP_ALLOWED_ORIGINS https://seu-app.vercel.app,http://localhost:5173 Origens exatas, com esquema, sem barra final. Nunca *

Você não precisa cadastrar SUPABASE_URL, SUPABASE_ANON_KEY nem SUPABASE_SERVICE_ROLE_KEY. O Supabase injeta as três automaticamente em toda Edge Function, e nomes com prefixo SUPABASE_ são reservados — a plataforma recusa o cadastro manual. É exatamente por isso que a service role key fica só no servidor: ela nunca passa pelo seu .env, pelo build do Vite nem pela Vercel.

Se a URL de produção mudar (domínio próprio, novo projeto na Vercel), atualize APP_ALLOWED_ORIGINS. A função responde 403 Origem não autorizada para qualquer origem fora da lista — inclusive a sua.

5.2 Publicar a função

Opção A — pelo painel (sem instalar nada):

  1. Edge Functions → Create a new function.
  2. Nome: admin-users (exatamente assim — o frontend chama esse nome em src/lib/adminApi.js).
  3. Cole o conteúdo de supabase/functions/admin-users/index.ts no editor.
  4. Mantenha Verify JWT ativado.
  5. Deploy.

Opção B — pela CLI:

npx supabase login
npx supabase link --project-ref <PROJECT_REF>
npx supabase functions deploy admin-users

5.3 Conferir

Em Edge Functions → admin-users → Logs, confirme deploy sem erro. Um teste rápido:

curl -s -i -X POST "https://<PROJECT_REF>.supabase.co/functions/v1/admin-users" \
  -H "Origin: https://origem-invalida.example" \
  -H "Content-Type: application/json" -d '{"action":"status"}'

Esperado: 403 com “Origem não autorizada”. Isso prova que o filtro de origem está ativo.

6.3 Publicar

  1. Importe o repositório na Vercel. O vercel.json já define build npm run build, saída dist e framework vite.
  2. Deixe o deploy de Preview concluir e teste tudo do passo 8 na URL de preview.
  3. Só então Promote to Production.
  4. Volte ao Supabase e confirme que a URL de produção está em APP_ALLOWED_ORIGINS (passo 5.1) e em Redirect URLs (passo 3).

Para testar a URL de preview, ela também precisa estar em APP_ALLOWED_ORIGINS. Como cada preview gera um subdomínio novo, o mais prático é validar a área administrativa direto em produção logo após a promoção, ou fixar um domínio de preview estável.

7. Usar a área administrativa

7.1 Ative o MFA na sua conta

  1. Entre no app com a conta administrativa.
  2. Aba Segurança → ativar verificação em duas etapas.
  3. Leia o QR no aplicativo autenticador e confirme o primeiro código.
  4. Saia e entre novamente, informando o código. Só assim a sessão vira AAL2.

Sem MFA confirmado nesta sessão, a área administrativa não aparece — e, por causa do has_required_aal() do passo 4, seus próprios dados também ficam ocultos.

7.2 Criar um usuário

  1. Abra a aba Configurações. O bloco “Administração de usuários” aparece no fim da página, e somente para UUID listado em APP_ADMIN_USER_IDS.
  2. Preencha Nome e E-mail.
  3. Clique em Gerar para a senha temporária (gerada com crypto.getRandomValues).
  4. Digite o código MFA atual no campo de confirmação.
  5. Criar usuário.

O código MFA é exigido de novo aqui de propósito: o servidor recusa a criação se a última confirmação de MFA tiver mais de 5 minutos (fresh_mfa_required). Se demorar preenchendo o formulário, basta informar um código novo e reenviar.

7.3 Entregar ao novo usuário

  • Passe a senha temporária por canal seguro e separado — nunca no mesmo e-mail do login.
  • No primeiro acesso o app abre a tela “Defina sua senha” e não deixa avançar sem trocar.
  • Após salvar, a sessão é encerrada e a pessoa entra de novo com a senha definitiva.
  • Oriente a ativar o MFA em Segurança logo no primeiro acesso.

Rollback do frontend

  1. Vercel → Deployments.
  2. Escolha o último deploy bom conhecido → ⋯ → Promote to Production.
  3. É instantâneo e não altera o banco.

Corrigir a Edge Function

Edite supabase/functions/admin-users/index.ts e publique de novo (passo 5.2). Não existe “desfazer” de secret: para reverter, cadastre o valor anterior. Em emergência, apagar o secret APP_ADMIN_USER_IDS desliga toda a administração — usuários existentes seguem entrando normalmente.

Estratégia corretiva no banco

Não edite um SQL já aplicado. Crie um novo arquivo em supabase/migrations/ no formato YYYYMMDDHHMMSS_descricao.sql, valide com npm run migrations:check, teste em homologação e só então aplique em produção. Migração aplicada é imutável.

Bloquear novas criações sem afetar quem já usa

  • Rápido: apague o secret APP_ADMIN_USER_IDS. A criação para; ninguém perde acesso.
  • Total: confirme Allow new users to sign up desmarcado (passo 3) — fecha também a API direta.
